### 1. 模块定位、三方映射与核心原则

#### 1.1 业务目标

M8 是 CrossPilot 平台的**组织治理、访问控制与安全审计底座**。跨境电商团队通常涉及选品、内容设计、客服、仓管、运营、BI 分析师、主管与管理者等多角色协作，若缺乏刚性权限隔离与留痕机制，极易出现：
1. 普通员工绕过审批给自己开通主管权限或修改线上合规/价格参数；
2. 业务单据由同一个人「自提自批」（如自己提交补货或退款单自己批准）；
3. 测试联调账号（`mock_buyer`）误看或误改真实店铺订单与采购数据；
4. 发生资金或线上事故后，无法用人话追溯「谁在何时对哪张单据做了什么操作、为何被放行或拦截」。

#### 1.2 三方编号对齐映射表

| 原型与现行路由 | 子模块名称 | 老师《模块需求细化 V1.1》对应 | 《SRS V1.0》需求编号 | 后端模块 / 前端视图 |
|---|---|---|---|---|
| `m8a` (`/m8/users`) | M8-1 员工名册与岗位授权 | M10 公共管理与任务审核（成员与岗位授权） | CM-01, CM-02 | `m8_org` / `M8UsersView.vue` |
| `m8b` (`/m8/roles`) | M8-2 岗位权限矩阵与审计 | M10（参数/策略版本、操作与拦截审计台账） | CM-03 ~ CM-07 | `m8_org` & `core/` / `M8RolesView.vue` |
| `/home` | 岗位协同工作台首页 | 全平台待办汇总与按岗位业务导航起点 | — | `m2_m3_bi` / `HomeWorkbenchView.vue` |

#### 1.4 五项核心治理原则（硬约束）

1. **禁止自批与职责分离（SoD）**：M0 成本改价、M1 售后退款、M4 选品过会、M6 补货审批、M7 发布放行五大敏感审批流，必须强制核验「发起人 ≠ 审批人」（`M7_STRICT_SEPARATION_OF_DUTIES=true`），同人自批一律返回 `403 M7-4032`。
2. **权限矩阵只读透明 + 越权必留痕**：M8-2 的权限矩阵仅供只读核对，绝不允许直接在页面点选绕过后端权限校验；任何岗位触发 `403` 拦截时，即使请求失败回滚，底座依然独立提交写入 `core_audit_events` 中文拦截记录。
3. **多租户硬隔离（`org_id`）**：JWT 或请求头中声明的 `actor_org_id` 必须与请求路径 `{org_id}` 严格一致，否则直接拒绝跨组织访问（`403 M7-4031`）。
4. **双模式身份认证与凭证零泄露**：线上生产走账号密码登录签发 `HS256 JWT`（V1.1 补齐 `/auth/login` 与密码哈希）；本地演示支持侧边栏切换 9 岗位 Header 模式；所有异常与日志经过 `redact_secrets` 脱敏，绝不吐出密钥或 Token。
5. **配置与参数版本向前生效**：组织级审批策略切换仅影响新审批动作，历史单据与历史审计记录保持原决策依据不可篡改。

### 3. 分页详细功能需求

#### 3.1 M8-1：员工名册与岗位授权（`m8a` / `/m8/users`）

1. **成员列表展示**：工号 (`user_id`)、员工姓名 (`display_name`)、企业邮箱 (`email`)、所属岗位徽章、在职状态（`在职启用` / `已停用`）、入册时间。
2. **新增成员授权**：
   - 必填：`user_id`（组织内唯一，重复抛 `409 M7-4091`）、`display_name`、`role_code`（必须是 9 大标准角色之一，否则 `422`）、`email`。
   - 仅 `manager` / `approver`（权限码 `m8:manage`）可创建，创建同时写中文审计 `USER_CREATED`。
3. **在线调岗与账号启停**：支持变更员工 `role_code` 及切换 `is_active`；写入 `USER_UPDATED` 审计句，且不改写该员工历史上在其它模块留下的审批/操作签名。
4. **V1.1 迭代规划**：新增真实登录页（`LoginView.vue`）与 `POST /api/v1/auth/login` 接口、为 `m8_users` 扩展 `password_hash` 与 `allowed_shop_ids`（店铺级行级数据范围绑定）。

#### 3.2 M8-2：岗位权限矩阵与审计（`m8b` / `/m8/roles`）

1. **九大岗位权限矩阵（只读）**：表格展示 9 个角色编码、中文名称、职责说明及完整权限码列表（`m0:*` ~ `m8:*`）。
2. **五大审批流策略台账（`M8ApprovalPolicy`）**：展示各模块审批策略名称、触发阈值规则、审批岗位、是否强制 `enforce_sod`（禁自批）及启用状态；支持 `m8:manage` 人员切换策略并写 `POLICY_TOGGLED` 审计。
3. **全平台中文操作审计台账**：
   - 支持按模块筛选（全部 / `M0` / `M1` / `M2` / `M3` / `M4` / `M5` / `M6` / `M7` / `M8` / `RBAC`）。
   - 每行显示：发生时间、所属模块、动作标识、执行状态（`允许` 绿标 / `拦截` 红标）、操作人及角色、关联 SKU、完整中文句子（`sentence_zh`）与链路 `trace_id`。

### 5. 非功能需求与验收标准

#### 5.1 性能、安全与可用性指标

1. **鉴权与拦截延迟**：每次请求 `get_actor_context` + `require_perm` 校验开销 ≤ 2ms；审计台账分页检索 P95 ≤ 60ms。
2. **安全拦截率**：越权操作、跨租户请求、停用账号访问拦截率 100%，且拦截审计记录独立提交成功率 100%。
3. **脱敏与不可篡改**：日志脱敏 `redact_secrets` 覆盖率 100%；前端不提供任何删除或修改历史审计的接口。

#### 5.2 核心验收标准矩阵（M8-AC-01 ~ M8-AC-06，对齐 M10-A01~A07）

| 验收编号 | 对应老师用例 | 给定条件与动作 | 通过标准 |
|---|---|---|---|
| **M8-AC-01** | M10-A01 | 查询 `/m8/roles` 与 `/m8/policies` | 精确返回 9 个角色及其权限码集合、5 大模块默认开启 `enforce_sod=true` 的审批策略 |
| **M8-AC-02** | M10-A07 | 无 `m8:manage` 权限角色（如 `planner`/`cs`/`creator`）新建或修改员工 | 返回 `403 M7-4031`，且 `/m8/audits?module=RBAC` 留存完整中文越权拦截记录 |
| **M8-AC-03** | M10-A07 | `mock_buyer` 尝试访问 M0/M2/M4/M5/M6/M7/M8 任意只读或写入接口 | 全部返回 `403`，仅 `/m1/simulator/ask` 允许调用 |
| **M8-AC-04** | M10-A07 | 携带 `X-Actor-Org-Id: org_other` 访问 `org_demo` 资源 | 租户门禁立即抛出 `403 M7-4031` |
| **M8-AC-05** | M10-A02 | 对员工调岗或停用，检查历史审批单与审计记录 | 调岗写入新审计事件 `USER_UPDATED`，历史单据原经办人签名与审计句不被篡改 |
| **M8-AC-06** | — | 日志或异常文本中意外出现 `sk-xxx` 或 `Bearer xxx` 凭证 | 经 `redact_secrets` 脱敏为 `***REDACTED***`，普通错误信息绝不泄露真实密钥 |

## 第3篇 M0 店铺接入、商品主档与仓储盘点需求

> **文档状态**：V1.0 正式基线（对齐《AI跨境电商平台-模块需求细化_V1.1》M02、《AI跨境电商平台V1.0-软件需求规格说明书》ST-01~02 / DT-04 及原型 `docs/prototypes/web/pages_m0_m3.js`）
> **适用范围**：M0-1 店铺授权管理（`m0a`）、M0-2 商品成本与订单台账（`m0b`）、M0-3 分店库存与人工盘点（`m0c`）

---

### 1. 模块定位、三方映射与核心原则

#### 1.1 业务目标

M0 是 CrossPilot 全平台的**事实底座与主数据中枢**。在跨境多平台（Amazon、TikTok Shop、Shopee、Lazada、eBay）运营场景下，M0 旨在解决五大长期业务痛点：
1. 店铺授权分散、Token 过期无人知晓，导致订单拉取中断或混入演示测试数据虚增实盘营收；
2. 同款商品在不同站点使用不同店铺 SKU/ASIN，缺乏统一内部编码（SKU）导致毛利核算与采购备货口径混乱；
3. 采购成本与头程运费被一线随意改写，导致历史毛利报表突然跳变且无人审批留痕；
4. 仓库刚卸货未清点残次品就自动增加线上可售库存，引发线上超卖发不出货；
5. 同一批外部订单重复同步或重复导入 CSV 时发生双倍记账，或采集失败当天被错误记为零销量。

#### 1.2 三方编号对齐映射表

| 原型与现行路由 | 子模块名称 | 老师《模块需求细化 V1.1》对应 | 《SRS V1.0》需求编号 | 后端模块 / 前端视图 |
|---|---|---|---|---|
| `m0a` (`/m0/shops`) | M0-1 店铺授权管理 | M02 店铺同步与测试数据管理（授权校验、同步批次） | ST-01, ST-02 | `m0_catalog` / `M0ShopsView.vue` |
| `m0b` (`/m0/ledger`) | M0-2 商品成本与订单台账 | M02（自有商品档案、真实销量去重、测试成本批次） | ST-01, DT-04 | `m0_catalog` / `M0LedgerView.vue` |
| `m0c` (`/m0/inventory`) | M0-3 分店库存与人工盘点 | M02（多状态库存口径、在途隔离、安全水位） | ST-02, DT-04 | `m0_catalog` / `M0InventoryView.vue` |

#### 1.3 上下游接口契约（仅限跨模块衔接）

  - M4-3 测款终审通过的新品（`M4SelectionService.decide_candidate` 写入/升级 `M0Product`，标明 `origin="M4_APPROVED"` 与审批依据）；
  - M6-4 到货质检与收货凭证（仅产生质检与在途核销记录，**严格禁止绕过盘点直接替代人工清点**）；
  - 运营或管理者导入的店铺授权信息、CSV 订单/历史销量批次、人工盘点实数与 1688 参考报价。
- **下游输出**：
  - `contracts/product_catalog_contract.py`：向 M7 内容创作子系统暴露只读 `ProductFactSnapshot`（SKU、名称、类目、品牌、售价、划线价、规格与卖点，屏蔽敏感采购成本与供应商资料）；
  - M1-2 导购知识库与 M1-3 售后赔付校验：按 SKU 核对本店在售商品与订单参考编号；
  - M5 销量预测与 M6 智能补货：供给 `M0Product`（`unit_cost_usd`、`moq`、`pack_size`、`lead_time_days`）与 `M0Inventory`（实时净可售 `on_hand`）；
  - M2 经营大屏与 M3 智能问数：按组织聚合实盘店铺与订单（**严格过滤 `is_mock=False`**）。

#### 1.4 六项核心产品原则（硬约束）

1. **实盘与演示严格隔离（MOCK Isolation）**：任何 `is_mock=True` 的店铺、订单、报价必须显式标注「仅演示不计营收」或「模拟比价层」；M2 实盘营收汇总与 M5 真实销量预测严禁混入 `is_mock=True` 数据。
2. **收货不自动改库存，盘点才改库存（Stocktake Redline）**：M6-4 仓库收货登记只留档收货数量、不良品数量与质检凭证；分仓库存 `on_hand` 的正式校准必须由仓库/物流人员在 M0-3 提交人工盘点单触发（V1.1 在服务端统一收敛为：收货只核减 `in_transit` 与待上架留痕，盘点确认后才写入 `on_hand`）。
3. **成本变更审批与职责分离（SoD）**：修改 `M0Product.unit_cost_usd` 必须通过 `M0CostRequest` 发起申请并填写业务原因；**申请人（`proposer_id`）绝对禁止自批（`reviewer_id != proposer_id`）**，批复前主档成本保持旧值不变。
4. **订单业务键防重与缺失不填零**：订单导入/同步按 `(org_id, order_id)` 严格去重，重复提交只跳过计数不翻倍；某天接口失败或授权失效时保留失败状态与最后成功时间，绝不把缺失日当成零销售。
5. **可售口径不重复扣减占用**：若来源库存 `on_hand` 已代表当前可用净库存，另列的 `reserved`（占用锁定）仅作展示参考，下游 M5/M6 取用时不可再次扣减成 `on_hand - reserved`。
6. **1688 模拟比价隔离**：`M0SupplierQuote` 标记 `is_simulated=True`，只作采买比价提示，绝不静默覆盖正式 `M0Product.unit_cost_usd`。

1. **统一商品主档区**：

2. **成本变更申请与审批区**：
   - `planner` 选择 SKU 填写 `new_cost_usd >= 0` 与必填业务原因（`reason` ≥ 2 字）提交，状态为 `PENDING`，保留 `old_cost_usd` 与 `proposer_id`。
   - `approver` 审批：系统校验 `proposer_id != actor.user_id`（违者 `403 M7-4032`）；批准（`APPROVED`）后立即更新 `M0Product.unit_cost_usd` 并写审计，驳回（`REJECTED`）则维持原价。
3. **订单台账与 CSV 批量导入**：
   - 订单表按时间/单号倒序显示 `order_id`、`shop_id`、`sku`、`order_date`、`qty`、`revenue_usd`、`is_mock` 标签与状态。

4. **1688 供应商参考报价区**：只读展示供应商名称、人民币单件价、MOQ、交期及 `is_simulated` 模拟比价层声明。

#### 3.3 M0-3：分店库存与人工盘点（`m0c` / `/m0/inventory`）

1. **分仓库存台账**：按 `(warehouse_code, sku)` 独立展示，支持多仓（如 `WH-US-WEST` 美西海外仓、`WH-TH-BKK` 曼谷仓、`WH-CN-SZ` 深圳总仓）。
2. **低库存红字预警与口径展示**：展示 `on_hand`（净可售）、`in_transit`（在途，未到仓不可售）、`reserved`（占用参考，不重复扣减）、`last_stocktake_by`；`on_hand < 30` 高亮预警并引导前往 M6 补货。
3. **人工盘点校准表单**：仅 `warehouse` (`m0:inventory:edit`) 可提交盘点单（`warehouse_code`, `sku`, `counted_qty >= 0`, `reason`）；保存后立即更新 `on_hand = counted_qty` 并实时联动 M5/M6 缺口重算。

#### 1.4 六项核心产品原则（硬约束）

1. **四源数据性质隔离与防演示混入**：严格区分「内部实盘选品」「外购行业估算」「平台热销公开」「仅演示数据」。文件带 `mock`/`demo`/`演示`/`测试` 字样却选择正式来源时拦截；外购估算品只作参考观察或「临时待核价」，不可直接批准投产。
2. **未舍入毛利精确比对门槛**：利润率计算保留小数精度（`round(..., 4)`），真实值 `29.996%` 面对 `30%` 门槛不可因展示四舍五入放行；缺失成本与运费时不填零，必须标明待核价。
3. **规格件数锁定与配件隔离**：配件报价不得混入整套商品成本；切换销售套装件数或修改规格时必须重新核价与重算物流/利润，保留历史记录。
4. **FBA 与 FBM 成本口径区分 & 物流周期红线**：FBM（单件拿货+头程+尾程+抽点，常规上限 30 天）与 FBA（拿货+海运+配送+抽点+仓储+10% 预留广告，常规上限 90 天）不可混算或靠隐瞒费用凑利润。
5. **侵权证据透明（模型分 ≠ 法律结论）**：商标命中或外观专利相似度评估仅作为证据呈交人工复核，禁止把未经校准的模型相似度直接等同于“保证不侵权”；检索失败不可宣称通过。
6. **测款终审职责分离（SoD）**：`selector` 提交待审后，必须由 `approver` 拍板；**提交人（`submitter_id`）绝对禁止自批（`403 M7-4032`）**。

   - 文件名含 `mock/demo/演示/测试` 而选正式来源时直接拦截报错；
   - 自动按「可投产（≥10% 毛利且非外购）」「临时待核价」「风险拦截」三类分诊统计入池。

#### 3.2 M4-2：选品工作台与决策（`m4b` / `/m4/workbench`）

1. **左列候选清单与右列深度评估台**：实时调整目标售价、采购价、头程、五维评分（`demand`/`competition`/`margin`/`supply`/`compliance`）及选品运营建议（`operator_note`）。
2. **双状态提交按钮**：
   - 「保存评估」→ 重算毛利与总分，状态更新为 `EVALUATING`；
   - 「保存并提交审批」→ 状态锁定为 `PENDING_APPROVAL`，并记录 `submitter_id = actor.user_id`。
3. **V1.1 增强规划**：增加「只看可投产」过滤开关、2~4 款商品横向并排对比表、批量勾选送审与商标/专利风险证据字段。

#### 3.3 M4-3：测款终审拍板（`m4c` / `/m4/approval`）

1. **待审队列呈现**：高亮毛利率是否满足硬门槛、五维综合分、提交人及推荐理由。
2. **硬门禁与审批**：
   - 审批意见（`note`）非空必填；
   - `submitter_id == actor.user_id` 强制抛出 `403 M7-4032`；
   - 同意测款（`APPROVED`）时在同一事务内创建/更新 `M0Product`，并可选择联动触发 M7 首版草稿任务（V1.1 补齐可选自动触发开关）；
   - 驳回（`REJECTED`）保留历史评语与原值，不写入 M0 主档。

### 1. 模块定位、页面映射与核心原则

#### 1.1 业务目标

M1 统一治理跨境多站点客服咨询、售前导购 FAQ 与售后赔付审批流程，解决四大典型运营风险：
1. 客服回复时错发竞品或别家店铺商品链接（串店风险），或中英文报价不一致；
2. 详情页承诺（M7）与客服实际回答口径矛盾，导致买家投诉“货不对板”；
3. 测试人员使用真实买家号反复下单测试客服话术，污染实盘客诉率与订单台账；
4. 同一客服自己新建售后退款单又自己批准打款，造成资金内控漏洞。

#### 1.2 原型路由与前后端映射表

| 原型与现行路由 | 子模块名称 | 核心业务定位 | 后端模块 / 前端视图 |
|---|---|---|---|
| `m1a` (`/m1/sessions`) | M1-1 客服会话与售后建单 | 会话接待、回复提交、核验订单并起草售后退款工单 | `m1_cs` / `M1SessionsView.vue` |
| `m1b` (`/m1/faqs`) | M1-2 客服导购商品库 | 按 SKU 维护买家痛点与 FAQ，单向同步供 M7 文案引用 | `m1_cs` + `voice_faq_contract` / `M1FaqsView.vue` |
| `m1d` (`/m1/simulator`) | M1-4 买家咨询模拟测试 | 内部安全模拟进线（`is_mock=True` 彻底隔离，绝不外发真实平台） | `m1_cs` / `M1SimulatorView.vue` |
| `m1c` (`/m1/aftersales`) | M1-3 售后审批与退款凭证 | 主管终审退款（禁自批）、联动扣减 M2 净利润 | `m1_cs` / `M1AftersalesView.vue` |

#### 1.3 上下游接口契约

- **上游输入**：`M0Product` 在售 SKU、买家咨询进线（模拟进线 `M1-4` 或平台会话同步）、`M0Order` 订单号参考。
- **下游输出**：
  - `contracts/voice_faq_contract.py`：向 M7-1 文案与 M7-3 视频分镜供应只读 `VoiceFaqSnapshot`（痛点列表 + FAQ 问答对），保证详情页卖点与客服回答同源。
  - M2 经营核算：汇总所有 `status == "APPROVED"` 的售后工单金额（`approved_refund_usd`），实时扣减净利润。

#### 1.4 五项核心业务原则（硬约束）

1. **模拟进线绝对隔离（`is_mock=True`）**：M1-4 发出的任何模拟咨询必须强制打标 `is_mock=True` 与 `channel="Buyer Simulator (MOCK)"`，绝不调用外部真实买家发送通道。
2. **测试买家最小沙盒权（`mock_buyer` 强制隔离）**：`mock_buyer` 岗位**仅拥有 `m1:simulator:run` 一项权限**，禁止访问任何真实订单、成本、会话台账与售后退款列表。
3. **售后退款职责分离（SoD）**：`cs` 提交的售后赔付单必须由 `approver` 审批；系统严格核对 `submitter_id != actor.user_id`（同人返回 `403 M7-4032`）。
4. **导购知识库与 M7 文案同源**：M1-2 更新 FAQ 后立即在 M7-1 上游参照区可见，修改 FAQ 权收敛至运营（`planner`）并写审计。
5. **禁止客服 AI 越权承诺直接退款**：所有赔付或退款必须走 M1-3 主管审批，V1.1 扩充发送前 3 项合规检测（金额一致、本店链接、双语数字一致）及打款凭证上传闭环。

#### 3.4 M1-3：售后审批与退款凭证（`m1c` / `/m1/aftersales`）

1. 展示所有售后工单、退款金额（USD）、原因、凭证说明与提交人。

- **上游输入**：`M0Product`（采购成本 USD、MOQ、箱规 `pack_size`、交期 `lead_time_days`）、`M0Inventory`（实时可用 `on_hand` 与在途 `in_transit`）、`M5SalesHistory`（剔除当日未完结订单的真实历史日销量）。
- **下游输出**：
  - M6-3 批准生成的 `M6PurchaseOrder` 承诺资金汇总至 M2 经营大屏（`po_commitment_rmb`）；
  - M6-4 到货质检与 M0-3 盘点校准闭环联动 `M6AlertEvent`（V1.1 严格收敛：收货只核减 `in_transit` 并留痕待上架，经 M0-3 盘点确认或合格入库后自动消警）。

#### 1.4 七项核心业务原则（硬约束）

1. **纯计算与框架隔离**：所有销量还原、滚动回测、安全库存、ROP、两步取整与状态流转规则由 `domain/` 纯函数实时计算，绝不硬编码业务数字。
2. **缺货日还原与历史缺失不填零**：当日末库存为 0 引起的断货低销须标注或还原真实潜在需求，同时永久保留 `qty_raw`；无任何销量记录的新 SKU 直接阻断并返回 `422 M5-1003`，绝不编造历史曲线。
3. **覆盖窗口匹配原则**：用于采购决策的预测跨度必须覆盖「总提前期（生产+物流）+ 审阅覆盖期」；不足不可静默替代。
4. **MOQ 与整箱两步取整约束**：正净需求 `net > 0` 必须先 `max(net, MOQ)` 再向上取整为 `pack_size` 整数倍；净需求 `<= 0` 时直接返回 `0`，不得因 MOQ 强行采购。
5. **路线可靠性与假设透明声明**：`sea`（45 天）、`air`（7 天）、`rail`（25 天）、`truck`（18 天）均显式标注演示假设参数属性，不得伪装为实时承运商报价。
6. **严密状态机与职责分离（SoD）**：`draft -> pending_approve -> approved -> closed`（或 `rejected`），`created -> shipping -> partial_received -> fully_received`（或 `cancelled`）。任何非法跃迁抛 `422 F-2001/2002/2003`；**提交人（`submit_user`）绝对禁止自批或自驳回（`403 M7-4032`）**。
7. **收货质量与库存口径规范**：不良品 `defect_qty` 不可计入合格可售库存；V1.1 严格收敛「M6-4 登记收货与质检留痕核减 `in_transit`，经 M0-3 盘点确认后写入 `on_hand` 并联动关闭 `M6AlertEvent`」。

### 3. 分页详细功能需求

#### 3.1 M5-1 ~ M5-3（销量预测与复盘）

1. **M5-1 (`m5a`)**：展示各 SKU 历史销量覆盖天数、平均日销与可选预测策略门槛（如：历史天数 `< 14` 天提示仅用短期均线或新品参考）。
2. **M5-2 (`m5b`)**：选择 SKU、运输路线（`sea`/`air`/`rail`/`truck`）、决策目标（`sales`/`profit`/`cash`），调用 `/supply/forecast/{sku}` 展示：
   - 多模型回测表（SMA / EWMA / Holt / Croston 等 WAPE/MAE 对比及 `best_model` 标识）；
   - 安全库存 `SS`、再订货点 `ROP`、目标库存、两步取整建议补货量 `qty_suggest`；
   - 14 天逐日需求预测与 4 路线全维对比明细。
3. **M5-3 (`m5c`)**：核对回测误差率（WAPE = 绝对误差之和 / 实际销量之和；实际合计为 0 时不可强算，标 N/A）与偏差方向，由 `bi_analyst` 沉淀复盘总结（`M6WeeklyReview`）。

#### 3.2 M6-1 ~ M6-4（补货测算与采购履约）

1. **M6-1 (`m6a`)**：What-If 沙盒允许调节生产交期覆盖（0~90天）、审阅周期（1~90天）、服务水平（0.90~0.99）、需求倍率（0.3~3.0x），实时输出基线 vs 仿真对比。
2. **M6-2 (`m6b`)**：强制基于有效 M5 预测（缺预测阻断），展开各路线覆盖天数与缺货风险后一键创建 `draft` 补货单（锁定 `snapshot_json`）。
3. **M6-3 (`m6c`)**：
   - `planner` 提交 `draft` → `pending_approve`；
   - `approver` 核对快照与提交人（禁自批）后批准 → 立即创建 `M6PurchaseOrder`（`status="created"`）并增加 `M0Inventory.in_transit`；或填写非空理由驳回 `rejected`。
4. **M6-4 (`m6d`)**：
   - `warehouse` 对 PO 执行 `ship`（发货在途）→ 分批 `receive`（输入实收 `receive_qty > 0` 与不良 `0 <= defect_qty <= receive_qty`，禁止累计实收 > `order_qty`）→ 全收自动置 PO 为 `fully_received` 并联动原申请单变为 `closed`；
   - 支持对未终态 PO 填写非空原因 `cancel` 并自动回退在途数；支持确认 `OPEN` 断货告警（`ACKED`）。

6. **大屏浏览者与操作权分离**：`manager` 具备全局只读浏览权，但不能直接越权修改广告出价或篡改竞品数据；写操作权限精准收敛至 `planner` / `bi_analyst`。
