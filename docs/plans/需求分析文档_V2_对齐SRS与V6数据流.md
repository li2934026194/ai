## 1. 概述与本版核心纠偏说明

### 1.1 编制目的与核心价值主张

本需求分析文档把《AI 跨境电商平台 V1.0 软件需求规格说明书（SRS）》、V1.1 架构图与真实数据流向图转化为**可逐模块把控、可出前端原型、可落库编码、可定量验收**的工程基线。

系统贯穿的核心价值主张是：在不越过平台合规红线、不把估算或演示数据当作真实经营事实的前提下，把跨境电商运营中的「**客服应答 → 驾驶舱看数 → 经营问数 → 选品研究 → 销量预测 → 补货决策 → 商品内容创作**」串成可追溯、可审计、可人工把关的工作链路，使操作者随时能回答四类问题：
1. **数据来自哪里**（内部真实 / 外购估算 / 公开观察 / 演示模拟）；
2. **哪些指标可算、哪些仍是未知**（未知值保持空值 `NULL`，严禁默认为 `0`）；
3. **哪一步由规则算出、哪一步由 AI 辅助解释**（金额、数量、日期与状态门禁由服务端确定性规则完成）；
4. **谁批准了下一步**（关键动作留存审批人、理由、版本与时间审计）。

### 1.2 从 V5 到 V6 的关键纠偏摘要

核对《V1.0 软件需求规格说明书》后，本版文档与 V6 数据流向图对早期草稿进行了 4 项根本性纠偏：
1. **角色权限精简**：取消此前过度拆分的 9 个孤岛岗位与超纲审批门槛，对齐 SRS §1.5 与仓库 `pilot/rbac/service.py`，收敛为 **6 个核心后台角色**（`admin`、`planner`、`cs`、`approver`、`warehouse`、`viewer/auditor`）；「买家(模拟)」仅作为 M1 演示入站页面触发方，不计入后台管理角色。
2. **模块定位回归**：「7 个 Agent 子模块（M1~M7）+ 1 套公共底座」为主干，恢复 **M2 驾驶舱设计器**（草稿/发布双版本、自然语言编排、4 卡并发问数）与 **M3 智能问数**（三条只读路径）的真实定位，移除脱离 SRS 的重型财务红字月结单、独立知识库上传大模块等超纲内容。
3. **保留业务闭环底座且严守库存边界**：完整保留**店铺、订单、商品与库存**公共底座（不砍掉店铺，确保选品/预测/补货/客服有完整上游事实）；同时严守 SRS §1.6、FR-RP-10、AC-RP-04 规定——**M6 补货审批与收货凭证登记绝不直接修改库存，库存实际变化仅由底座的「独立库存同步流程」完成**。
4. **去掉无依据的超纲卡点**：移除未在 SRS 中出现的三档金额参数表、全局 30 秒缓冲真撤回与 10 因子跨模块节点签名，仅保留 SRS 明确要求的全表 `org_id` 隔离、`Idempotency-Key`、数据库行锁 + `version`、M6 提交时的 `fact_signature / history_signature` 校验，以及待补齐的真实 RBAC 鉴权（替换演示头 `X-Actor-Role`）。

### 1.3 明确非目标与不作声称事项（SRS §0.3）

以下事项属于本阶段明确非目标或外部约束，不得在设计与验收中伪装为已具备的生产能力：
- **Amazon 买家消息接入**：Amazon SP-API Messaging API 只写不读，无收件箱接口；当前演示环境通过「模拟买家页」入站，正式工程路径需通过邮件中继（IMAP/POP3）实现并视为受限外部依赖。
- **智能客服 AI 定位**：不声称自主决策 Agent；由规则意图识别、可选模型翻译、向量检索与人工确认组成。
- **售后工单外部状态**：内部工单批准只推进内部状态，不触发 Amazon 外部退款/退货/换货，`external_status` 始终保持 `UNKNOWN`。
- **演示鉴权边界**：现有 `X-Actor-Role: SUPERVISOR` 与前端固定 `demo-supervisor` 仅为演示头，必须在生产级底座中替换为真实登录与 RBAC 鉴权（对应风险 R-01 / 待确认 Q-01）。
- **外部数据与选品演示**：未连接真实站点专用爬虫与付费 API；演示同步仅生成 `MOCK` 事实，不得用于真实采购与利润核算。
- **内容生成边界**：文案生成由确定性内容策略基于商品目录事实产生草稿，界面「AI」为产品用语；商品图与短视频调用外部 ComfyUI，生成完成不等于视觉合规通过或已自动发布。
- **问数与补货边界**：智能问数不执行改价/删改写操作；补货测算值不代表已向供应商下单，也不自动修改库存。

### 2.2 全局数据流向总图

对应原型文件：`docs/prototypes/dfd_v6/d00_system_data_flow.png`

全局数据流分为三层协同闭环：
- **第 0 层（公共底座）**：维护 `Shop → Order / OrderItem → Product / ProductSourcing → 独立库存同步(InventoryPosition)` 与统一网关/真实 RBAC 鉴权；所有记录强制带 `org_id` 租户键。
- **第 1 层（商品经营闭环）**：`M4 选品（投产） → M7 内容创作（文案/视觉） → M1 智能客服（售前推荐与售后核验） → M5 销量预测（真实日销量预测与 WAPE 评估） → M6 智能补货（强制读取未来 ForecastRun → 审批与履约凭证）`。
- **第 2 层（经营分析中枢）**：`M3 智能问数` 从公共底座只读读取经营快照与库存，通过 `QAClient.answer_query()` 为 `M2 驾驶舱设计` 提供布局预览与发布后大屏实时重算能力。

## 3. 组织权限体系（精简 6 角色 RBAC 模型）

对应原型文件：`docs/prototypes/dfd_v6/d00_rbac_roles.png`

### 3.1 角色收敛映射（对齐 SRS §1.5 与 `pilot/rbac/service.py`）

为解决此前 9 个岗位过度拆分的冗余问题，本平台将 SRS §1.5 描述的 9 类操作场景职责映射为 **6 个精简后台 RBAC 角色**（外加演示测试入口「买家(模拟)」）：

| 角色代码 | 角色名称 | 对应 SRS §1.5 职责 | 对应 `pilot/rbac` 基础角色 | 核心权限边界 |
| --- | --- | --- | --- | --- |
| `admin` | 系统管理员 | 连接器配置、训练知识/模型依赖状态、用户角色配置 | `admin`（系统运维域） | 负责组织、用户、角色、连接器与工作流/模型配置；不参与日常客服、选品与补货业务审批 |
| `planner` | 运营 / 选品 / 内容 / 设计员 | 驾驶舱设计者/业务运营、选品研究员、内容创作人员、补货计划提交人 | `planner` | 负责维护商品基础、驾驶舱编排发布、选品导入与测款申请、预测画像与执行、补货计划预览与提交、文案与视觉生成送检（**不可自批补货与测款**） |
| `cs` | 客服人员 | 客服 | `cs`（新增业务角色） | 查看译文与推荐商品、人工核对发送中英文回复、接管投诉会话、核验买家订单并创建售后工单（**不可自批工单**） |
| `approver` | 主管 / 审批与审核人 | 主管/审批人、内容审核人员 | `approver` | 负责审批/驳回售后工单（行锁+version）、选品评审与测款批准、补货计划审批（`approver ≠ planner` SoD）、内容人工合规复核与发布审批 |
| `warehouse` | 采购 / 仓库 / 物流人员 | 采购/仓库/物流人员 | `warehouse` | 负责登记采购单凭证、多批次质检收货记录、发货运单凭证，以及触发公共底座的**独立库存同步**（不越权审计划） |
| `viewer` / `auditor` | 大屏浏览 / BI / 只读审计 | 大屏浏览者/管理者、数据分析/BI 人员、审计员 | `viewer` + `auditor` | 只读查看已发布驾驶舱、使用智能问数并维护指标口径、查看全系统操作与鉴权审计日志（**零业务写权限**） |
| *测试入口* | *买家（模拟）* | *买家（模拟）* | *非后台角色* | *仅在 M1 模拟买家演示页触发英文咨询/投诉入站，不进入后台 RBAC 管理矩阵* |

### 3.2 核心权限与安全约束
1. **租户隔离（FR-COM-01 / BR-COM-04）**：所有持久化业务表均含 `org_id`，任意接口读写前必须在服务端校验资源与当前登录人所属 `org_id` 一致，跨组织直接拒绝（403/404）。
2. **真实实时鉴权（R-01 / Q-01）**：替换演示头 `X-Actor-Role: SUPERVISOR` 与固定 `demo-supervisor`，每次请求按数据库实时查询用户角色与权限码（参考 `pilot/rbac/service.py` 的 `has_permission()` 设计），不信任旧 Token 快照。
3. **职责分离（SoD, FR-RP-08）**：补货审批、售后工单审批与选品测款批准必须校验「审批人 ≠ 提交人」。
4. **越权审计（FR-COM-05）**：所有写操作及 403 越权拒绝均写入操作/鉴权审计日志（记录操作人、结论、理由、版本、时间）。

## 4. 模块 0：公共底座需求分析

对应原型文件：`docs/prototypes/dfd_v6/d08_base_foundation.png`

### 4.1 业务事实主数据闭环
1. **店铺与连接器接入（`Shop`）**：保留完整店铺管理，记录 `org_id`、平台（Amazon / Shopee / Lazada / TikTok Shop）、站点、授权状态与消息适配器配置（Amazon 仅演示或邮件中继；东南亚三平台按官方 API 适配）。
2. **订单主表（`Order / OrderItem`）**：以 `(order_id, platform, org_id)` 唯一去重；显式区分真实成交订单与演示数据，分别供 M1 售后订单核验、M5 日销量归集、M6 智能分支非演示历史使用。
3. **商品主数据（`Product / ProductSourcing`）**：维护 SKU、标题、品类、属性、成本卡与跨平台映射基础，统一供 M4 选品、M5 预测、M6 补货、M7 内容创作使用。
4. **独立库存同步流程（`InventoryPosition`）**：作为全系统**唯一允许改写库存数值的独立流程**，记录可用库存、安全库存、在途状态及 `SYNCED` 同步状态与时间戳；M1 工单与 M6 补货只读引用，绝不直接改写。

### 4.2 统一技术契约（FR-COM-01 ~ 08）
- **请求/响应封装**：前端统一经 `apiRequest` + `orgApi` 调用 `/api/v1/orgs/{org_id}/...`，携带 `X-Api-Envelope: 1`；M7 二进制素材文件下载接口直接返回二进制流，不走 JSON 解包。
- **读写边界与幂等并发**：读接口不得产生设计行写入；所有写操作支持 `Idempotency-Key` 或数据库行锁 + `version` 防重复提交与并发覆盖；写操作在同一数据库会话内写操作日志并提交。
- **降级与真源**：可选 LLM 不可用时必须回退确定性规则或显式标示不可用，不得静默失败；数据库为最终事实真源，实时通道仅作通知，断线以 HTTP 回读兜底。

## 5. 模块 1：M1 智能客服 Agent 需求分析

对应原型文件：`docs/prototypes/dfd_v6/d01_cs_agent.png`

### 5.1 核心目标与两条商品路径边界
将售前商品依据、买家来信、人工中英文回复、售后订单核验与内部工单审批收敛于同一会话上下文，提供无需向真实买家发信的可重复演示环境。必须严格区分两条独立商品数据路径：
- **主工作台推荐目录（`CustomerRecommendedProduct`）**：面向 Milvus 向量语义检索。
- **V2 售前子模块（`CustomerListing`）**：人工核验 Listing，面向 V2 规则匹配。

### 5.2 功能需求与数据流
1. **推荐商品建库与召回（FR-CS-06 ~ 10）**：
   - 上传 XLSX 模板，先完整解析校验价格、用途、人群、平台域名及整表合法性，再按 `(org_id, shop_id, sku)` upsert 并置 `INDEXING`；
   - 异步每 20 件一批生成向量并校验数量与维度后写入 Milvus，回写 `READY/FAILED`；
   - 推荐接口按买家原文（截断 ≤ 1000 字符）召回并回表过滤 `ACTIVE/READY`、预算与本店，最多返回 3 件及依据；前端用请求序号与 `conversation_id` 防止旧请求覆盖新会话。
2. **消息入站、意图分析与双语回复（FR-CS-11 ~ 21）**：
   - 模拟买家页仅展示 Amazon 店铺并提取已有买家名，支持 `INQUIRY / COMPLAINT`，重试保留 `client_message_id`；
   - `POST /inbound` 校验组织/店铺/会话/幂等 ID，写 `Conversation`、`ConversationMessage`、`CustomerIntentAnalysis`，事务提交后向本组织 WebSocket 广播 `MESSAGE_RECEIVED`；已知简单句即时翻译，其余异步翻译并广播 `MESSAGE_TRANSLATED`（不可用时标不可译待人工）；
   - WebSocket `EventHub` 仅维持当前进程内连接，前端断线时每 3 秒通过 HTTP 回读兜底；
   - 工作台加载会话并行读消息、上下文与最近 V2 意图分析（明确标注规则分析不是自主决策）；遇到售前词或 `PRESALE_ADVICE` 且无退款/损坏词时自动触发 Milvus 推荐；
   - `POST /replies` 须经过人工核对确认与稳定幂等 ID，**后端硬拦截**未核实退款/到货承诺、非当前店铺链接、中英文数字/型号不一致；落库 `DELIVERED_MOCK` 并广播。
3. **售后订单关联与工单审批（FR-CS-22 ~ 27）**：
   - 售后页仅列出 `MOCK-AMAZON-*` 会话；仅当最新入站被标记为 `AFTER_SALES_COMPLAINT` 时，`GET order-candidates` 才按最近消息订单号检索本店订单，否则仅按买家名给出「可能匹配」提示（不得自动建立关联）；
   - 关联订单须先取得买家确认并提交证据类型与 `FBA/FBM`，由 `POST /order-links` 校验属本店后入库 `ConversationOrderLink`；
   - 创建工单（`RETURN / REFUND / REPLACEMENT / EXCHANGE_VARIANT`）须校验：属已核验订单行、件数 ≤ 原订单行、退款 ≤ 订单总金额、理由 5–1000 字、附件 ≤ 10 件（单件 ≤ 5MB，仅 PDF/JPG/PNG/DOCX/TXT 存 PostgreSQL，下载二次鉴权）；**且后端须补齐校验会话为 `HUMAN`（修复 R-02/Q-02 前后端口径不一致）**；
   - `approver` 提交 `version`、批准/驳回与理由，后端以真实权限 + DB 行锁 + `version` + `PENDING_REVIEW` 状态同时满足才更新内部状态并使 `version+1`；`external_status` 始终保持 `UNKNOWN`。

### 5.3 验收要点
- 重复 `client_message_id` 仅生成一条消息；WS 广播必在数据库提交后发生；断线 3 秒内 HTTP 回读补齐。
- 违规回复（未核实退款承诺/外链/中英文数字不一致）被后端拦截且不落库。
- 并发审批同一 `version` 仅一个成功，且 `external_status` 维持 `UNKNOWN`。

## 8. 模块 4：M4 选品分析 Agent 需求分析

对应原型文件：`docs/prototypes/dfd_v6/d04_selection_agent.png`

### 8.1 数据性质隔离与异步接入（FR-SEL-01 ~ 05）
1. **四种数据性质显式区分**：`INTERNAL`（内部实际）、`PAID_EXTERNAL`（外购估算）、`OPEN_PUBLIC`（公开观察）、`MOCK`（演示）。外购与公开数据可辅助研究，**绝不可单独支撑实际经营利润与测款批准**（BR-SEL-04）。
2. **异步导入与防重**：限制文件 ≤ 25 MB，CSV 按 UTF-8 BOM 读取，XLSX 只读解析限制解压 ≤ 150 MB、≤ 50 列、≤ 50,000 行；计算 SHA-256 按组织去重（外购来源去重键含数据商及采购凭证），接口创建 `QUEUED` 任务并立即返回 `202`，异步转 `RUNNING → SUCCEEDED/FAILED` 并按 `(SKU, 平台, 地区, 周)` 写入 `WeeklyFact`；前端轮询状态并刷新来源/任务 Tab。

### 8.2 确定性计算、初筛与测款决策（FR-SEL-06 ~ 14）
1. **确定性财务口径（未知保持空值）**：
   - 净销量 = 支付件数 − 退款件数；净收入 = 销售总额 − 折扣 − 退款金额（退款未知则净收入未知）；
   - 商品成本 =（采购单价 + 头程单价）× 净销量；毛利 = 净收入 − 商品成本；
   - 经营利润 = 毛利 − 平台费 − 履约费 − 退货费 − 仓储费 − 广告费（任一必需费用未知时不生成经营利润）；
   - 趋势：至少 4 周数据，计算后半段与前半段周销量均值相对变化（前半段均值为零则趋势未知）。
   - 自动标注状态：`DEMO_ONLY`、`ESTIMATE_ONLY`、`BLOCKED`（高合规风险）、`NEED_DATA`。
2. **规则初筛排名**：要求 ≥ 4 周且净收入与趋势可算，排除模拟/阻断/已拒绝/已批准测款；支持三种权重模式（均衡 0.5/0.4/0.1、收入 0.7/0.2/0.1、增长 0.25/0.65/0.1）；**利润率未知时不按 0 参与，而在可用权重内重新归一并提示缺失**。可选 LLM 仅解释排名，不可用时回退规则摘要。
3. **人工评审与测款**：
   - 批准测款硬门槛（由 `approver` 审批）：**纯 `INTERNAL` + 缺失项为空 + 经营利润已知 + 经营利润率 ≥ 10% + 无高合规风险**；
   - 测款规则建议预览：实际收入达目标 90% 且利润为正且利润率 ≥ 10% 建议 `PRODUCE`；已亏损建议 `DELIST`；单价异常（低于一半或高于两倍）优先建议核对数据；其余建议 `SUPPLEMENT`；最终由人工选择决定，选择 `PRODUCE/DELIST` 后结束测款并更新研究档案状态。

## 9. 模块 5：M5 销量预测 Agent 需求分析

对应原型文件：`docs/prototypes/dfd_v6/d05_forecast_agent.png`

### 9.1 需求画像、模型策略与真实日销量（FR-FC-01 ~ 06）
1. **先验画像与版本锁**：由商品品类生成未核验先验 `DemandProfile`，人工保存采用数据库行锁 + 版本号校验，成功后版本递增；`forecast_selection.recommend()` 仅给出候选模型、适用理由与条件，不构成精度承诺。
2. **模型注册与依赖校验**：`ForecastModelDefinition` 登记统计、间歇、树模型、深度/基础模型策略；`available()` 检查服务器运行依赖，自定义模型不可绕过适配器校验；未启用、缺依赖或历史不足时前端明示原因且后端拒绝执行。
3. **真实日销量归集**：从 `Order / OrderItem` 查询本组织可售状态订单，按业务日期聚合，**空日补零、排除当日未结束销量**（最长取约一年历史）。

### 9.2 预测执行、回测与 WAPE 评估中心（FR-FC-07 ~ 12）
1. **线程池异步预测**：重新校验资格后在线程池运行策略 `predict()`（7/14/30 天）及一步滚动回测，结合库存生成补货参考并落库 `ForecastRun`（记录训练截止日、模型版本与评估来源）。误差带来自历史一步绝对误差随预测期扩展，**明确标注不代表经校准的 P80 或统计置信区间**。
2. **模型评估中心**：核对订单来源与平台范围（演示/跨平台不匹配时不评准确率），按 SKU、店铺/平台/国家、日/周/月、预测周期与大促/淡旺季对齐到期实际销量，**识别并排除缺货日期**以免把受限销量误认为真实需求；计算：
   - `WAPE = Σ|实际销量 − 预测销量| ÷ Σ实际销量 × 100%`（参考管理区间：≤5% 非常优秀、5–10% 优秀、10–20% 良好、20–30% 一般、>30% 较差，具体正式门槛见 Q-07）；
   - 同时输出 `Bias`、`MAE` 与区间覆盖率；支持带审计信息的人工实际修正并完整保留原始预测与订单事实，评估结果供 M6 读取。

## 10. 模块 6：M6 补货预测 Agent（拓展）需求分析

对应原型文件：`docs/prototypes/dfd_v6/d06_replenish_agent.png`

### 10.1 普通分支 vs 智能分支并列设计（FR-RP-01 ~ 04）
两个入口共享 `ReplenishmentPlan`、事件与审批履约接口，以 `snapshot.planning_mode` 区分，列表互不混入：
- **A 普通分支（单仓 SKU 三方案）**：输入 `InventoryPosition`、`Product`、`ProductSourcing`、最近未来 `ForecastRun`（缺失时仅以 `Product.sales_30d / 30` 做带警告代理）与版本化 `ReplenishmentCostCard`；经确定性 `calculate()/project()` 算出「保销量 / 保利润 / 保现金」三方案及逐日库存曲线。
- **B 智能分支（拓展：多路线与安全库存）**：输入当前仓位、**强制已保存未来 `ForecastRun`（缺失直接返回 `FORECAST_REQUIRED`）**、非演示成交订单日销量与历史路线/人工报价/仓位分配/服务水平（无事实源参数前端留空由用户填写并记录依据）；经 `calculate_plan()` 对比海/空/铁/公路路线。
- 两条分支的预览接口均为**只读不落库**，返回建议量、资金、风险、曲线与 `fact_signature`（智能分支含 `history_signature`）；可选 AI 仅撰写定性采购摘要文字，数量、金额与日期全由规则算出。

### 10.2 计划提交、审批状态机与履约凭证（FR-RP-05 ~ 11）
1. **提交重算门禁**：提交 `POST /plans` 必须携带 `Idempotency-Key`、`fact_signature` 与预期数量；普通计划强制校验库存状态 `SYNCED` 与有效成本卡；智能计划强制校验未来预测与非演示订单历史。后端重取当前事实重算，签名或数量不符即拒绝提交，校验通过才写入 `READY_FOR_REVIEW` 计划与 `SUBMITTED` 事件。
2. **状态机与职责分离**：状态主线为 `READY_FOR_REVIEW → APPROVED → EXECUTING → PURCHASE_ORDERED → INSPECTED → SHIPPED`（待审可转 `REJECTED`），事件严格按计划+类型去重；`approver` 审批必须不同于提交人（SoD），版本号随状态推进。
3. **凭证登记与库存红线**：`warehouse` 人员登记采购单号/报价、多批次质检收货记录（独立收货批次表，多批收货期间保持 `PURCHASE_ORDERED` 直至收满或确认最后一批）与发货运单。**补货测算不代表已向供应商下单；审批与凭证登记绝不直接修改 `InventoryPosition`，库存变化由公共底座的独立库存同步流程反映**（AC-RP-04）。
