1.1目标
这条链路把售前商品依据、买家来信、人工回复、售后订单核验与内部审批放在同一个会话上下文中。客服可以追溯“推荐了哪个商品、依据是什么、买家说了什么、核验了哪笔订单、谁批准了工单”，减少凭记忆复制链接、按姓名误认订单和未经核实承诺退款的风险。它也是一个可重复的 Amazon 客服演示环境，无需向真实买家发消息。

POST /agents/customer-service/runs

CustomerRecommendedProduct

1.1 
Amazon：邮件中继是唯一可编程路径
如上一轮所述，Amazon SP-API的Messaging API是
只写不读
的——没有inbox资源，没有“获取买家消息”的操作，Notifications API也没有“买家消息到达”的事件类型。可行的工程路径是
电子邮件中继
：
在Seller Central的“通知首选项→买家消息”中，将平台指定的接收邮箱填入转发地址；
通过IMAP/POP3拉取Amazon转发到该邮箱的买家消息，解析邮件正文与订单号的关联；
回复时，通过同一中继地址（或Amazon SES）发回，保持邮件线程完整，使Amazon将其识别为对原始对话的回复。
这条路径
不在SP-API的保障范围内
，Amazon调整中继规则时可能断裂，需要在架构上将其视为“外部依赖”做降级设计（如转发中断告警、手动兜底入口）。
合规红线
：Amazon明确禁止在买卖家消息中包含营销内容、外部链接和主动触达超出订单必要范围的信息。更重要的是，Amazon的AI系统正在主动扫描消息内容判定合规性，全自动AI回复一旦越界，可能导致消息权限被限制。因此，Amazon通道的AI回复
默认应走“草稿+人工确认”模式
，将全自动回复限制在严格白名单场景（如纯物流状态查询）。
1
.2 Shopee / Lazada / TikTok Shop：官方API可用，但需逐平台适配
这三个东南亚主力平台均提供官方消息API，但字段结构、授权流程、可用消息范围各不相同。Shopee和TikTok Shop的响应指标（首响率、12小时回复率）会直接影响店铺评分，这意味着接入不仅是“能收消息”，还需要实时性保障。
接入层建议采用统一领域模型 + 适配器的设计：定义UnifiedMessage（包含平台、店铺、会话ID、买家ID、订单号、正文、语言、时间戳、情绪标签等标准字段），每个平台实现各自的MessageAdapter负责拉取/发送/状态同步。Ecommerce4j SDK的适配器模式可以作为参考架构——其核心思路是“屏蔽API差异，上层业务只依赖统一接口”。但需注意该SDK作者明确标注仅供学习参考，生产环境需要自行维护。
1
.3 接入中台的职责边界
消息接入中台统一承担：
连接管理
（OAuth token刷新、IMAP连接池）、
消息归一化
（映射到UnifiedMessage）、
去重与排序
（同一买家跨平台/跨店铺的消息去重）、
路由分发
（根据平台+店铺+紧急度投递到对应Agent会话）、
回执与状态同步
（发送结果写回各平台）。中台不承担业务逻辑，只做“消息的标准化进出”。

此图的 Router 是代码中的路由类及其处理函数，不代表 ORM 实体方法。关键实现及源码注释：
1. `import_products()`：先完整解析并校验文件，再按本店 SKU upsert；提交数据库后异步索引。
2. `index_vectors()` / `index_products()`：20 件一批生成嵌入，检查向量数量/维度，写 Milvus；索引结束后为本次商品记录 `READY/FAILED` 与错误。
3. `recommend_products()`：按当前组织/店铺做向量召回，再回表过滤 `ACTIVE/READY`、预算和店铺，最多返回 3 件。
4. `mock_inbound()`：以 `client_message_id` 去重，写会话、消息、意图；提交后广播，再异步补全译文。
5. `complaint_order_candidates()`：只在最新入站被标记投诉时查找；从本会话最近消息提取订单号，限定组织/店铺，结果仍需人工核验。
6. `mock_reply()`：确认中英文、风险承诺、本店已登记 URL、数字/型号一致性后才落库并本地广播。
7. `verify_order()` / `new_case()`：核对买家确认、当前店铺订单及订单行归属，限制数量与退款金额。
8. `decide_case()`：主管头、数据库行锁、版本和待审状态同时满足才改变内部状态；外部状态不变。
9. 前端 `loadComplaint()`：工单原因取最新买家消息；类型预选取会话最近一次明确的退款/替换/换货/退货诉求，避免后续只补订单号时误改类型，客服仍可手动调整。
10. 前端 `findRecommendedProducts()`：限制查询长度符合 API 契约，并以买家原文优先；会话/请求编号防止旧请求覆盖新会话。

1.8 实现步骤
### 1.8.1 推荐商品
1. 建 `CustomerRecommendedProduct` 与店铺关联，给组织/店铺/SKU 加唯一约束；准备 XLSX 模板和字段别名。
2. 在 `recommendation_router.py` 完成文件、价格、用途、人群、平台域名与整表校验，成功后 upsert 并标 `INDEXING`。
3. 按 20 件一批调用嵌入服务并写 Milvus，回写 `READY/FAILED` 与错误；前端轮询或手动重建。
4. 推荐时按会话店铺查询向量，再回 PostgreSQL 复核店铺、状态、价格，返回最多 3 件及依据。
### 1.8.2 Amazon 消息模拟
1. 从 Amazon 店铺和其订单提取可选买家；由页面生成稳定 `client_message_id`。
2. 入站校验店铺/会话、按 ID 去重，写会话、消息及规则意图；提交事务后广播 WS。
3. 即时词典/模式或异步配置模型翻译；失败时保留原文和不可译标记。买家/客服页 WS 事件后 HTTP 回读，断线轮询。
4. 模拟出站在人工确认、承诺/链接/数字校验后写草稿与消息，再广播送达通知。
### 1.8.3 客服工作台
1. 并行加载消息、上下文和最近分析；根据最新入站触发投诉候选或售前推荐，防止旧请求覆盖当前会话。
2. 规则意图分析与推荐分别返回风险和商品依据；客服可重新分析或手动接管。
3. 中文回复经快捷译文或翻译接口生成英文草稿，人工核对后提交模拟回复，保留幂等 ID。
4. 发送成功后页面刷新会话；复杂退款、退货问题进入售后核验流程。
### 1.8.4 售后工单
1. 读取投诉消息与候选订单；人工接管并取得买家与订单关联证据。
2. `POST /order-links` 校验组织、会话店铺与订单，保存核验人、证据类型、引用和履约方式。
3. 根据已核验订单行创建无附件或含附件工单，校验类型、数量、金额、文件；初始 `PENDING_REVIEW`。
4. 主管提交版本和理由，后端行锁校验后更新内部状态；保留外部状态 `UNKNOWN`。
驾驶舱设计Agent（讲解）
借助AI将最关键核心指标数据进行个性化可视看板展示，设计效果包括桌面、平板、手机各种终端设备进行适配显示，还可以设置配置不同颜色，不同的布局显示，支持拖拉拽交互，可以显示不同样式，还支持AI自动生成文字描述信息，将编排好的可以预览与发布，一亘发布成功，智能BI驾驶舱显示的就是发布的最新设计大屏显示
此Agent的价值在于把“驾驶舱搭建”从依赖开发排期的报表工程，变成业务人员可自然语言编排、实时预览、可控发布、持续刷新的智能 BI 工作台；同时通过“草稿/发布双版本 + 布局快照 + 实时问数”的机制，兼顾线上稳定与数据实时。
2.1目标
经营驾驶舱是业务侧查看核心指标的主要入口，但搭建过程长期依赖数据开发与
前端开发：指标、图型与版式由业务提出需求，经排期开发、联调后才能上线，一次
改动往往牵涉多方协同，搭建门槛高、调整周期长。与此同时，设计过程中的版式调
整与线上大屏相互牵制，未完成的布局容易被误发布，已上线的版式又可能随编辑持
续漂移。智能 BI 驾驶舱设计工作台针对这两类问题，把驾驶舱的搭建能力直接交给业务人
员，并把“设计态”与“发布态”分离管理，使大屏版式保持稳定、经营数据保持实时。
对业务与运营人员而言，价值集中在“不必等排期”：搭建与调整都在设计页完
成，改版不再需要数据开发与前端开发全程介入。对数据分析与 BI 人员而言，价值集
中在“配置可复用、故障可隔离”：每个组件独立问数，固定指标有稳定路径，单点异
常不会拖垮整屏。对管理者与大屏观看者而言，价值集中在“版式可信、数据可信”：
看到的版式是发布快照，看到的数值是当前数据。
智能 BI 驾驶舱设计工作台面向业务人员提供自然语言编排、组件库拖拽、实
时预览和 AI 卡片描述能力，让经营大屏从“提需求等开发”变为“业务自助搭
建、可控发布”。系统采用草稿与发布双版本、布局快照与实时问数分离的设
计：编辑不影响线上，发布版版式稳定，组件数值按当前数据实时刷新；单张
组件问数失败可被隔离，不影响整屏展示；未发布时自动回退旧驾驶舱，保障
业务连续性。该能力复用平台智能问数底座，兼顾搭建效率、发布安全、数据
实时性与大屏可用性。

## 一、可直接复制到 Word 的排版稿
**WAPE 销量预测准确度评价指标**
**——跨境电商销量预测与补货 Agent 模型评估说明**
### 1. WAPE 计算公式
WAPE 全称是 **Weighted Absolute Percentage Error（加权绝对百分比误差）**，用于衡量模型预测销量与实际销量之间的整体偏差。
WAPE = [Σ|实际销量ᵢ − 预测销量ᵢ| ÷ Σ实际销量ᵢ] × 100%
**示例：某 SKU 连续三天销量预测**
| 日期 | 实际销量 | 预测销量 | 绝对误差 |
|---|---:|---:|---:|
| 第一天 | 100 | 90 | 10 |
| 第二天 | 200 | 220 | 20 |
| 第三天 | 300 | 280 | 20 |
| 合计 | 600 | 590 | 50 |
计算：
WAPE = (10 + 20 + 20) ÷ (100 + 200 + 300) × 100% = 8.33%
**结论：** WAPE = 8.33%，说明预测总绝对误差相当于实际总销量的 8.33%。
### 2. WAPE 数值如何判断？
以下为业务管理参考目标，并非所有行业通用标准。WAPE 越低越好。
| WAPE | 评价 | 说明 |
|---|---|---|
| ≤ 5% | 非常优秀 | 预测误差较小 |
| 5%～10% | 优秀 | 预测效果较好 |
| 10%～20% | 良好 | 基本满足业务需求 |
| 20%～30% | 一般 | 需要优化模型 |
| ＞30% | 较差 | 需要检查数据和模型 |
### 3. WAPE 与其他预测指标的区别
| 指标 | 全称 | 主要用途 |
|---|---|---|
| MAE | 平均绝对误差 | 衡量平均差多少件 |
| RMSE | 均方根误差 | 对大误差惩罚更明显 |
| MAPE | 平均绝对百分比误差 | 衡量每个预测点的相对误差 |
| WAPE | 加权绝对百分比误差 | 衡量整体销量预测偏差 |
| Bias | 预测偏差率 | 判断预测整体偏高还是偏低 |
WAPE 相比 MAPE 的优势是：销量大的 SKU 或日期对整体误差贡献更大，不容易被低销量商品的百分比误差过度影响。
### 4. 在跨境电商 Agent 中如何使用？
建议在销量预测 Agent 中增加一个独立的模型评估模块。
**销量预测模型评估中心**
- WAPE：8.33%，预测误差较低
- 预测偏差 Bias：0.5%，轻微高估
**模型评估维度**
- 按 SKU 评估预测误差
- 按店铺、平台、国家评估
- 按日、周、月评估
- 按 7 天、14 天、30 天预测周期评估

**架构建议**
将 WAPE 纳入销量预测 Agent 的模型评估体系，并把评估结果传递给补货预测 Agent，形成：
历史订单 → 销量预测 → WAPE 模型评估 → 库存与交期分析 → 智能补货 → 实际销量回流 → 模型持续优化
这样才能真正建立一个有反馈、有评估、有优化能力的跨境电商 AI 运营闭环。
**缺货期间的特殊处理**
缺货期间的实际销量可能低于真实需求，因此计算 WAPE 时最好识别缺货日期，避免把被库存限制的销量误认为真实需求。

7. **接入前端。** 模型算法页显示画像/候选/注册表；销量预测页展示可执行性、预测曲线与本地导出；评估页显示状态、误差及修正入口。
