### 旧方案的适用范围

原竞品查询工具的约 20 个工作日估算仅覆盖查询子项目，且按单人本机使用假设。它不是本次 10 模块两周交付的依据。沿用其中的数据真实性、来源证据和持续观察设计，人员、排期与部署以本方案重新评审。

现有 units_30d 的 actual／estimate 类型不能直接容纳公开购买量标识，现有按 ASIN 翻页也不满足销量参考降序。两项均列入 D4 的明确改造任务，禁止把旧字段重命名后当作新口径已经实现。

### 为什么按这个顺序

首先验证能否持续得到有用的商品、货源和店铺数据。没有这些证据，选品和预测页面即使完成，也不能承担运营工作。随后建立权限、任务、参数版本与人工审核，供所有 Agent 共用。

商品采集与店铺同步是两条不同数据路径：前者服务竞品选品，后者提供自有真实销量和库存。店铺授权在 D1 发起，D5 目标完成首次同步；权限未就绪时记录阻塞，不把可登录卖家后台当作接口授权完成。

选品先实现 FBM 的最小真实链路，再在同一个费用模块补齐 FBA 差异；两种模式都属于本版验收。选中商品后，内容制作和采购分析在业务上可以独立启动；日程中的先后只是本轮开发安排。

问数与看板最后接入统一指标，是为了复用已经验证的业务记录。它们不能建立另一套销量、利润或采购金额计算。

## 4 前两天必须验证的能力

两天用于快速判断路径是否成立，不足以证明全类目覆盖、长期稳定或每日一万条处理能力。持续采集稳定性从 D1 或最早可运行时开始记录，至少跨 3 个实际 24 小时更新周期检查。样本规模属于本方案建议。

| 验证项 | 最小验证动作 | 通过证据 |
| --- | --- | --- |
| G01 商品发现与字段 | 先取约 50 至 100 条真实链接，覆盖多个入口、类目及 FBA／FBM；区分新商品发现和已知链接复抓。 | 保存价格、日期、购买量原文、归属、模式、缺项和失败证据；不能用旧开放目录替代当前数据。 |
| G02 1688 规格与价格 | 选 3 至 5 个实际商品，至少包含配件低价、套装差异和缺重量场景。 | 确认访问、搜图和 SKU 价格路径；可比货源有单件价依据，不能只返回搜索结果封面价。 |
| G03 店铺真实数据 | 检查开发者应用、授权角色及至少一个自有店铺；核对几个 SKU 的销量与库存。 | 账号可登录不等于接口已授权；记录回溯、字段和费用条件，延期审批单列。 |
| G04 商标专利及关键词 | 验证相关商标记录、外观专利图片、关键词候选及排序来源。 | 有可回查来源；检索失败与未发现记录不同；无排名来源不造搜索量。 |
| G05 素材与视频 | 用一件商品生成文本、实际图像，并运行一个可用 ComfyUI 视频工作流。 | 验证模型工具调用与结构化输出、实际文件、运行时长及预算；只得到任务号不算完成。 |
| G06 平台草稿与素材路径 | 核查当前店铺创建原生草稿的可用方式，分别验证 A+ 和视频资格。 | 原生草稿必须在目标后台可回查。校验预览、库存设零和本地草稿均不能替代。 |

G01 与 G02 决定自动选品是否成立；G03 决定真实预测输入；G04、G05、G06 分别约束风险、内容与发布。模块未依赖的部分可以继续开发，整体是否完成仍按原需求验收。

### 双方分工

你负责提供真实业务样本、完成平台授权、确认费用口径和商品事实，并作选品、发布与采购的最终决定。我负责代码、数据结构、接口、页面接入、自动化检查、问题定位和文档。账户密码与密钥使用本地安全配置，不在聊天或普通日志中提交。

建议每天安排一段集中联调时间，并及时处理当天阻塞项；D2、D7、D10、D14安排业务走查。每天结束记录已验收结果、阻塞项和次日任务。Codex 协作依赖实际开启的开发会话与可用工具，不视为无人值守的长期开发团队。

### 工期怎样调整

以已通过验收的任务而非代码量计算进度。若任一关键路径滑动超过 1 天，立即更新剩余日程，优先消化非关键展示调整，不占用人工确认和数据正确性检查。外部审批或访问限制的等待时间单列。

两周内应保持第一版范围稳定。新增需求先登记；不能通过删去已确认的 FBA、视频、A+、问数或驾驶舱来悄悄兑现日期。必要的范围调整以具体差异表交你决定。

图 2  自主 Agent 调用受控专业工具  业务事实与执行上下文分别持久化

### 采用单个自主 Agent 的原因

当前的首要问题是验证模型能否根据证据继续研究，而不是建立六套 Agent 对话。单 Agent 定义可以同时服务多个隔离任务，多个商品不共用同一条长聊天记录。并发调用工具和批量处理商品也不要求多 Agent。

LangChain create_agent 提供模型工具循环；LangGraph 提供执行状态、检查点与人工中断恢复。FastAPI 处理用户身份、配置、审核和查询，独立 Worker 执行长任务；不在 HTTP 请求中等待整套选品或视频生成。

SQLite WAL 与本地文件目录用于单机小范围内测。业务表和检查点分别管理；多机或写入竞争达到实测瓶颈时迁移 PostgreSQL。现有界面和查询代码按模块复用。

每日采集与店铺同步直接由调度和 Worker 执行。模型仅处理需要判断的研究、创作与分析；外部等待、金额计算和更新调度不消耗模型轮次。

## 7 架构比较与框架选型

| 比较项 | A 固定流程加模型 | B 单自主 Agent | C 主 Agent 加子 Agent |
| --- | --- | --- | --- |
| 适合业务 | 稳定采集、计算、提交。 | 不确定研究、局部修正、问数。 | 多领域长任务和独立上下文。 |
| 主要收益 | 重复工作自动完成。 | 按反馈调整行动，减少接管。 | 专业分工、上下文隔离。 |
| 开发成本 | 较低；例外增多会增加分支。 | 中等；需工具、状态和评测。 | 较高；需委派、汇总与恢复。 |
| 耗时与用量 | 通常较易预测。 | 随研究轮次变化。 | 多出分派汇总；并行可能提速。 |
| 稳定与调试 | 路径清楚，适应性有限。 | 单任务轨迹较易复盘。 | 多轨迹与版本关联更复杂。 |
| 用户效果 | 适合常规操作。 | 能继续追查、解释和修正。 | 收益须通过对照评测证明。 |
| 扩展方式 | 增加流程分支。 | 增加专业工具或能力集。 | 独立扩展专业模块。 |

| 选型 | 在本项目中的用途与限制 | 决定 |
| --- | --- | --- |
| LangChain 和 LangGraph | 工具循环、检查点、人工恢复；业务权限和证据仍由项目实现。 | 采用 |
| CrewAI | 角色与层级委派直观；仍需建设业务版本、审批和运行约束。 | 可做对照实验 |

## 8 自主决策与业务代码边界

自主性的判据是：模型根据目标和新证据选择下一步工具、参数及停止条件。固定业务前置条件和 if else 校验仍有必要。模型不能通过更新计划绕过利润门槛、事实核实或人工发布确认。

| 模块 | 模型可以动态判断 | 代码与人工约束 |
| --- | --- | --- |
| M01 采集查询 | 必要时理解非结构化字段。 | 调度、去重、日期价格筛选和排序由代码完成。 |
| M02 店铺同步 | 通常无需自主 Agent。 | 同步、权限、去重、修订与对账。 |
| M03 选品 | 图片判断、货源复用、重检索、规格与风险证据研究。 | 费用计算、数据校验；未知待确认，最终人工选中。 |
| M04 内容 | 卖点、提示词、图文评价和局部修正。 | 真实事实约束、素材版本；人工审核内容。 |
| M05 草稿发布 | 解释平台错误、提出修正。 | 提交与回查；人工确认绑定实际内容版本。 |
| M06 预测 | 检查适用性、选择允许的分析方法和解释。 | 数值预测、回测与误差由工具计算。 |
| M07 补货 | 理解目标、比较情景、解释约束冲突。 | 库存交期、MOQ、箱规及预算计算；方案人工确认。 |
| M08 问数 | 理解提问、拆解查询与追问。 | 指标口径、权限、只读参数化查询。 |
| M09 驾驶舱 | 建议指标、结构化布局与解读。 | 允许的图表组件渲染；布局审核后发布。 |
| M10 管理 | 不需要自主决定管理规则。 | 权限、版本、预算、审核与审计。 |

### 不能由模型补齐的事实

没有找到的重量、1688 实际单件价、历史销量、竞品后台词及平台资格保持缺失。公开购买量区间不能改成精确销量。风险研究输出检索范围、线索和附图对照；未发现记录不等于无侵权。

目标是减少每件商品的人工检查时间，同时保留潜在机会。初筛不采用固定候选数量截断；预算不足的商品进入待处理，不标成不值得做。

## 9 工具调用与动态规划

### 一次决策循环

① 读取目标与参数快照，提取范围、交付物及缺项。② 模型用 write_todos 建立简短计划。③ 模型返回工具名和结构化参数。④ 执行层验证权限、Schema、业务前置条件和预算。⑤ 工具返回事实、证据、缺项或错误。⑥ 模型更新计划并选择继续、换方法、请求人工或提交结果。

计划是可更新的目标清单，不把完整研究流程写成固定顺序。商品已存在有效货源时先核实旧货源；遇到配件低价时调整检索；利润具备核算依据后才进入对应风险研究。业务依赖由工具校验，即使模型调用过早也不能产生无依据结果。

| 工具组 | 建议接口 | 服务端控制 |
| --- | --- | --- |
| 查询与货源 | inspect_product、search_sources、compare_specs。 | 商品证据、SKU、件数与价格条件；缺项显式返回。 |
| 核算与风险 | calculate_profit、search_trademarks、search_design_patents。 | 利润只读已验证成本；风险结果保存出处与检索范围。 |
| 内容与素材 | generate_copy、generate_images、submit_video、inspect_artifact。 | 事实版本、工作流白名单、产物校验；长任务只返回任务号。 |
| 经营分析 | query_metrics、run_forecast、calculate_replenishment。 | 受控指标、数据覆盖期、数值计算和回测。 |
| 人工与结果 | request_review、prepare_review_package。 | 认证审核人、版本匹配；最终状态由服务端确定。 |

### 注册与校验

工具注册表包含名称、用途、输入输出 Schema、读写性质、所需权限、前置条件、超时、可重试错误和成本等级。Pydantic 验证类型与取值，业务服务核实商品和证据关系；格式正确不代表报价真实。

店铺、根任务、配置版本和权限从服务端上下文注入，不让模型通过工具参数指定身份。第一版注册本地 Python 函数即可；跨应用复用时再考虑 MCP，不把它作为交付前提。

### 结果合格标准

结构校验检查字段与类型，业务校验检查规格、费用和版本，模型检查语义遗漏及可疑一致性，运营确认关键事实和最终决定。只保存解释文本不足以完成任务；审核页读取已核验的业务记录与证据。

## 10 可选主 Agent 与专业协作

第一版的自主运营 Agent 可演进为主 Agent。它负责目标、计划、选择专业能力、检查交付、调整策略、控制预算和汇总；不擅自改变经营门槛、店铺范围或发布权限。后续优先试验以下三类专业子 Agent，而不是按六个页面一一拆分。

| 专业子 Agent | 范围 | 边界 |
| --- | --- | --- |
| 商品研究 | 货源、规格、报价依据和风险证据。 | 不制作整套内容，不发布，不采购。 |
| 内容生产 | 八类内容、语义检查和局部修正。 | 不改变已确认产品事实，不自行发布。 |
| 经营分析 | 问数、预测方法、补货情景及看板建议。 | 数值交给工具，不修改真实库存或执行采购。 |

### 委派与消息协议

主 Agent 将子 Agent 作为工具自主选择。子 Agent 使用独立上下文，接收必要事实和证据引用，不复制完整对话。请求携带 root_task_id、task_id、parent_task_id、目标、输入版本、配置版本、允许工具及预算；授权身份由后端注入。

结果统一返回 status、结构化结果、证据引用、缺项、错误、产物版本和用量。status 区分 completed、needs_review、failed、partial。子 Agent 的最终自然语言只是说明，服务端验证交付合同后才能更新业务状态。

### 依赖 并行与一致性

后端登记依赖图，验证无环和必要业务前置条件，仅领取依赖满足的任务。不同商品研究、独立经营查询可以并行；内容依赖人工选中版本，视频依赖对应 Listing 和白底图。并行结果分开写入，聚合时校验输入版本；多人修改用 expected_version 防止覆盖。

长子任务先返回 child_task_id 并等待完成事件。子任务待人工时保留其检查点；恢复该子任务后再通知主任务，不能把同一目标重复当作新请求启动。已完成任务按输入版本返回已有结果；根任务取消传递到子任务。

所有子任务共享根任务调用、Token、费用和时间预算。第一版扩展只允许一层委派，不允许子 Agent 调用祖先或自由群聊。复杂度增加必须由效果评测证明收益。

官方依据  子 Agent 作为工具与上下文隔离

## 11 记忆管理与运行约束

### 短期状态与长期记录

短期状态放在 LangGraph 检查点，包含当前计划、消息、工具结果引用和待确认事项。每个任务拥有独立 thread_id，不跨店铺复用。上下文过长时只摘要已完成过程，保留不可丢失的约束、证据 ID、未解决事项和当前事实版本。

长期记录保存到业务表：历史货源、实际核价、排除原因、人工决定、渠道和配置版本。模型推测不能未经核实写成长期事实。复用前检查规格、来源有效性和价格；参数变更只影响后续任务。

第一版优先结构化查询与全文检索。资料规模和检索效果需要时再引入 RAG 或 pgvector，并带来源、时效与权限过滤。利润、库存、销量仍走精确查询与计算，向量检索不替代数据库。

### 失败与重新规划

| 情况 | 处理方式 |
| --- | --- |
| 限流或短暂故障 | 执行层按错误类型有限退避，不占用反复思考轮次。 |
| 规格不符或搜索无关 | 模型调整查询和证据策略；记录尝试差异。 |
| 缺重量报价或资格 | 补查无果转人工；不猜测，不把缺失当零。 |
| 权限失效或访问受限 | 停止相关访问，报告缺口和受影响交付。 |
| 远端提交结果不明 | 先回查任务号、SKU 和版本；不盲目重提。 |
| 无新证据或预算耗尽 | 保存部分结果与待处理项，停止自动循环。 |

### 安全与成本

网页与专利内容是资料，不是指令。工具只开放必要操作；不开放任意 SQL、Shell 或无限制浏览器。凭据留在服务端，日志脱敏。模型不能替用户批准发布或采购，审批必须绑定当前对象版本。

每次调用先原子预留预算，返回后按实际 Token 和费用结算；主子任务共享根预算，恢复不清零。配置调用数、最大输出、运行时长、并发及图像视频次数。相同工具与输入版本去重，连续无进展终止。调用次数上限不能代替金额预算。

## 13 选品到内容及采购的执行案例

以下是执行机制示例，A、B、C 为假设商品，不代表已经取得的实际研究结果。用户请求按美国站 FBM、当前价 20 至 35 美元、近三个月上架、近期购买量参考门槛 300 检查今日商品，同时检查自有 SKU 是否需要补货。

| 阶段 | 模型决策 | 代码执行与交付 |
| --- | --- | --- |
| 任务拆分 | 识别新品研究与在售补货两个目标。 | 固定范围、参数和数据性质，两个独立任务可并行。 |
| 商品 A | 识别已核实过的同规格旧货源。 | 核实当前报价与有效性，保存对照和证据。 |
| 商品 B | 发现低价结果只是替换头。 | 不采用配件价；修改 query 继续找整机，保留商品机会。 |
| 商品 C | 详情仍缺包装重量。 | 进入待确认，保存问题和恢复位置；其余商品继续。 |
| 利润核算 | 判断 A 的核算依据是否齐全。 | 按同发货模式和固定版本计算，保存费用明细。 |
| 风险研究 | 扩展相关商品词与外观结构检索。 | 附图、商标记录、未覆盖范围进入审核包。 |
| 经营分析 | 判断已有预测是否覆盖采购期。 | 期限不足则补做工具预测，计算库存、在途与采购情景。 |
| 汇总审核 | 解释候选、待确认、排除和未完成。 | 运营选中商品；采购方案由人工确认，线下执行。 |

### 人工选中之后

用户选中 A 后，系统固定商品事实与参考素材版本，调用内容工具制作八类交付。若附图错误呈现三件套而实际为单支，模型定位问题，只重做受影响图片并检查关联文案。Listing 与白底图就绪后提交视频任务，取得真实产物后再更新完成状态。

内容人工审核后进入原生草稿流程；正式发布仍绑定店铺、SKU 和内容版本。缺少竞品关键词排名依据时如实标识，不编造搜索量。采购输入包含测试成本时，方案明确显示测试影响。

方案 B 由同一个自主 Agent 配合专业工具完成上述判断。方案 C 才把研究、内容和经营分析分别委派；专业拆分不能改变业务口径或减少审核要求。

## 16 数据结构与来源设计

每个结果都要回答：属于哪家店铺或哪个竞品、来自哪里、是什么口径、何时取得、用哪个版本计算。公开观察、真实经营、测算、预测和测试输入分别标识，缺失不能保存为零。

| 数据组 | 核心字段与关联 | 关键约束 |
| --- | --- | --- |
| 商品与观察 | products；observations；marketplace、ASIN、parent、offer、observed_at。 | 站点与 ASIN 唯一；观察只追加，当前值指向最近可用观察。 |
| 购买量与价格 | raw_text、metric_kind、unit、lower／upper、window、ASIN_scope；金额和币种。 | 保留购买人数或件数等来源语义，不擅自把买家数变成售出件数。 |
| 货源与证据 | supplier_offers、spec_comparisons、evidence_files；SKU、单件条件、规格与图像。 | 整机、配件、套装分开；每个采用成本指向货源版本。 |
| 规则与利润 | config_versions、logistics_rates、fee_rules、profit_estimates。 | 保存配置、汇率和费用生效日期；重算生成新结果。 |
| 任务与人工审核 | jobs、job_steps、review_items、decisions、audit_events。 | 参数快照、输入版本、状态、lease、attempt、操作人。 |
| 内容与平台提交 | content_sets、assets、content_versions、submissions。 | 8 类内容分别记录状态；确认引用准确版本，平台对象可回查。 |
| 店铺销售与库存 | stores、sales_facts、inventory_snapshots、sync_runs。 | 店铺与 SKU 区分；订单行或来源主键去重；修订有记录。 |
| 预测与采购 | forecast_runs、forecast_points、purchase_plans、plan_versions。 | 期限、粒度、情景和依据明确；计划数量不能写成实际库存。 |
| 指标与会话 | metric_definitions、query_sessions、query_results、dashboard_versions。 | 问数与看板共用口径，布局草稿和发布版分开。 |

旧 SQLite 数据迁移前先备份并清点来源数、ASIN 数和缺失字段。旧记录不具备历史观测日期时不能补造；archive 保持历史来源。旧 units_30d 不直接迁移成公开购买量，先按原类型保留。

建议 UTC 保存事件时间，按选定店铺业务时区展示和汇总；美国站业务时区、促销取价、月份边界须在 D1 样本核对时确认。商品包装参数与裸机参数分列。

## 17 任务执行与人工确认机制

### 任务服务和 Agent 运行时各自负责什么

FastAPI 在事务中创建 job、输入与参数快照，返回 202 和 task_id。Worker 通过租约领取工作，调用 LangGraph 持久化 Agent。Agent 决定研究动作；任务服务负责队列、并发、取消和外部事件，不另建一套固定研究路径。

业务结果写入商品、报价、审核和内容表；检查点保存模型消息、计划和恢复位置。thread_id 与任务身份绑定，恢复使用原 Scope 和配置版本。浏览器关闭不应丢失已保存任务。

| 状态 | 含义与处理 |
| --- | --- |
| queued / running | 等待或执行；短事务领取和续租，同一任务限制并行恢复。 |
| waiting_review | 保存人工问题和 interrupt 标识；审核有效后恢复同一任务。 |
| waiting_external | 等待渲染或平台结果，由事件或 Worker 检查，不让模型循环询问。 |
| retry_wait / failed | 暂时故障有限重试；不可恢复问题记录失败及影响。 |
| reconciling | 远端可能已执行，按外部任务号及版本回查后决定下一步。 |
| succeeded / partial | 分项交付已核验才成功；必交素材或草稿缺失保持部分完成。 |
| cancelled | 取消尚未执行工作，传播到子任务；已发生的外部动作保留记录。 |

### 版本与重复执行

新任务使用最新参数；运行中任务及派生子任务继承原快照。待确认的原任务恢复不换配置。历史商品因涨价或新目标重新研究时建立新任务并关联旧记录，历史结论不改写。

工具调用以对象、动作、输入版本建立幂等键；人工确认带 expected_version 和唯一操作键。两人同时恢复、旧版本重审均应被服务端拒绝。外部提交先登记意图，保存任务号；超时后先回查再决定是否补发。

### 异常后如何继续

进程重启后回收过期租约，核对检查点与业务事件，再恢复任务。interrupt 前的代码可能重放，不能把不可重复副作用放在无保护的位置。调用预算持久化且恢复不清零，已完成产物按版本复用。

审核接口继续使用 POST /api/v1/reviews/{id}/decisions，验证后才执行 Command(resume)。建议增加任务事件读取和取消接口；主子任务恢复仅由经过授权的任务服务调用，前端不能任意指定 thread_id。

## 19 选品 Agent 方案

### M03 业务依赖与动态研究

选品必须具备查询依据、初筛结论、同规格单件报价、包装渠道、费用利润和风险证据，最终由人工决定。模型根据已有事实自主安排补查、复用或重检索；上述材料是交付依赖，不是每件商品一律照走的固定工具顺序。普通自动研究无需运营逐步点击。

1688 匹配输出功能、尺寸、型号、套装件数及销售单位的对照表。配件最低价单列而不入成本；货源比较保留实际 SKU 与价格条件。单件购买条件、登录价格或包装资料不明确时停止确定性利润判断。

### 费用计算由代码负责

FBM 成本包含单件拿货价、头程、尾程与平台抽点；FBA 成本包含单件拿货价、海运头程、配送、抽点、仓储与广告。使用同一币种与精确十进制计算，展示时才舍入；利润门槛默认 30%，29.996% 不能因显示 30.00% 而通过。

FBA 投广告初始预留售价的 10%，明确不投为零，不明确待确认；仓储默认 2 个月，支持商品覆盖。FBM 完整周期默认 30 天、FBA 90 天，按常用渠道和全流程最长时间判断，不以换渠道来凑利润。

平台费用采用有生效日期的官方规则；可用的 Product Fees API 估算用于核对。该接口需要相应授权和角色，不能代替所有缺失的包装资料，也不等于所有实际费用都已核实。

技术依据  Amazon 单 ASIN 费用估算与授权条件

### 风险与历史复查

美国商标查询保存检索词、记录和时间；外观专利保存查询范围与附图，模型标注相似结构和差异供人工核对。把握不足待确认。人工约 50% 的经验值不直接映射为模型分数或法律结论；未找到记录不保证无风险。

仅因利润不足而排除的商品，涨价后用新售价和保留成本粗算，同时重算比例费用；预计达门槛再转人工核实当期拿货价。确认同款的新链接可复用旧货源，但每个链接按自己的售价与发货模式重新核算。

验收使用三类真实样例：可继续、明确排除、证据不足。初筛宁可多留潜在商品；小、轻、带电和差异化属于排序偏好，不新增硬尺寸上限。

## 22 销量预测与采购补货方案

### M06 大模型调用数据与计算工具

为候选商品和自有在售商品建立不同输入路径。自有商品使用真实销售历史、库存、缺货记录和明确经营假设；候选新品使用已获得的可比资料。数据不足时输出缺项和需要确认的假设，不编造去年同期或日销量。

两周内建议先实现可解释基线：按可用历史使用近期均值或带权均值，并以历史时间切分回测检验；能够支持且有足够周期时再比较简单季节性基线。模型选择方法并解释结果，数值计算和回测由代码工具完成。方法、最少历史和有效期作为待确认参数。

输出预测期间、总量、可计算粒度、数据截止时间、方法、假设与版本。保守、基准和乐观是建议的情景，不称为统计置信区间。预测期必须覆盖采购至可售和之后销售窗口；FBA 不能仅用未来 30 天支持 90 天后到货的决策。

评估使用 WAPE、MAE 和数量偏差，并注明缺货影响。实际销量合计为零时 WAPE 不可计算；采用测试成本不影响真实销量本身，但涉及测试输入的派生结论必须标识。

### M07 方案计算与确认

先检查预测是否有效，再按时间推演真实可售、预测消耗和在途可售日期，分别识别到货前的缺货风险及到货后的需求。采用以下数量口径作为评审建议，确认后才成为正式计算规则。

建议数量为到货后覆盖期需求，加安全库存，减到货前预计可用库存及覆盖期其他有效在途，最低为零。在途只计算一次，缺货损失不默认是欠单，新品不把尚未到货阶段的潜在销量计入首批采购。

样例：300 件需求 + 20 件安全库存 − 80 件预计库存 − 50 件有效在途 = 190 件。按 MOQ 100 件和每箱 24 件向上取整得到 192 件。单价 20 元、物流 300 元，总额为 4,140 元；预算 4,000 元时显示缺口 140 元。样例全部为测试数据。

人工修改数量后重算金额、箱规与预算，记录理由和版本；零需求不因 MOQ 强制采购。确认只保存方案，不生成采购单、付款或真实在途。首版先完整实现一条可核对计算链，不引入跨商品资金最优分配。

## 23 问数 驾驶舱与公共管理

### M08 智能问数

建立受控指标字典：销量件数、订单数、销售额、可售库存、候选与排除记录、预测和采购方案。模型把问题解析成指标、店铺、商品、日期与对比条件；服务只允许调用已登记的只读查询工具，不将自由生成的 SQL 直接执行。

店铺范围由服务端会话权限注入，不能由提示词覆盖。连续追问继承明确条件；遇到利润口径、比较期间或对象歧义先澄清。结果引用实际查询记录，展示来源、截止时间和测试标识。删除会话不删除业务数据。

广告费用和实际经营利润的真实来源未确认时显示未接入。不可用的指标不能用广告预留比例或测试成本冒充真实支出；这些字段可以保留在指标目录供后续接入验证。

### M09 经营驾驶舱

组件库先覆盖商品开发、内容发布、销售库存、预测采购。自然语言生成结构化布局建议，前端在允许的图表类型、指标、过滤和样式范围内渲染；支持拖拽、大小与颜色调整、电脑平板手机预览。AI 不生成任意可执行页面脚本。

布局草稿与发布版分开，人工发布后才改变团队看到的布局。组件分别取数和显示错误；数据刷新不改变布局版本。AI 解释引用与卡片相同的结果版本，刷新失败保留旧值及旧时间。

### M10 团队 参数和任务

内部成员独立登录，按店铺与操作授权；有权限的人确认发布和采购。利润、物流、广告仓储、排除偏好、内容模板、预测与补货参数均有配置入口、单位、范围和生效版本。平台硬性要求不能作为任意运营数值覆盖。

参数改动只对后续任务生效，已有商品和运行任务不重跑。中断任务恢复沿用原配置；历史商品重新研究另建任务并关联旧记录。任务中心展示计划、工具轨迹、人工问题、来源错误和用量，分项呈现素材及外部提交状态。

### 第一版页面与接口的关系

原型中十个模块的页面作为导航和交互参考，不作为真实数据来源。卡片数字、图表、候选计数、审核状态都改由后端同一业务记录计算；本地模拟功能从正式环境构建中关闭。

## 25 部署 容量与成本

### 两周内测部署

建议先在一台常开主机运行 Web／API、数据库和后台任务，ComfyUI 在已验证的本机或独立设备运行。开发环境、测试数据与内测实际数据隔离，先备份再迁移；不沿用原型 localStorage 作为团队数据存储。

只有单台应用主机时使用 SQLite WAL，数据库放本地磁盘，不放多人共享网盘；任务写入保持短事务。若目标是多主机工作节点或实测写竞争明显，应迁移 PostgreSQL 并重新估时，不能把单机内测配置直接宣称为多机生产方案。

团队访问范围、HTTPS 和授权凭据保存方式在 D3 明确。备份覆盖数据库与素材清单；使用一致性备份方式，D13 至少执行一次恢复演练。备份留存天数与恢复目标需按实际设备和预算确认。

### 持续跟踪会使采集量增长

每日筛选后浏览约一万条是业务现状，不是每天新增一万条或全库只有一万条。已知商品规模等于初始规模加每日新增去重商品的累计；每 24 小时刷新全部已知商品的请求量随之增长。不能暗中停止已排除商品采集来维持表面完成。

容量演算：若库中 10 万商品每件平均 2 次请求，则仅复抓约 20 万请求每天，尚未包含发现和重试。若某条件命中率为 5%，要得到约 1 万结果，需约 20 万可查询商品。这是算术示例，实际覆盖、限速与成功率必须测量。

监控发现数、已知总量、24 小时内更新占比、缺项率、待确认数、积压、重试、单件 AI 成本及真实进入核价的数量。先用去重、已核查记录和明确规则减少重复模型调用；不以成本为由默默排除不确定商品。

### 费用边界

竞品数据采购预算保持 0 元，不自行引入付费数据库或付费采集代理。模型、图片视频算力、网络、存储和可能的官方接入费用另列，D2 按实际账号和服务确认。免费开源框架不等于数据取得、模型运行和长期服务器均免费。

成本上限、单任务调用次数和并发作为配置；超限暂停并说明原因，不切换到假结果。新增付费服务或外部托管须确认用途、资料范围和预算。本次设计文件仅本地保存。

### 必须贯穿验收的四条流程

E2E01 新品从真实采集到审核、八类内容与原生草稿，未经确认不发布。E2E02 真实销售库存到预测、含测试数据的采购方案与人工确认，真实库存不变。E2E03 参数变更后旧任务和历史保持原值，新任务使用新版本。E2E04 外部失败、测试字段与无权限店铺在所有页面一致显示，不能生成虚假零值或全量成功。

D14 的交付表按已通过、部分完成、未通过、因授权不可验证逐项列示。发现错误报价自动通过、跨店铺越权、未经确认发布、测试值冒充实际值等关键问题时，不开放对应自动业务动作。仅在全部适用验收满足后，才称为完整第一版交付。

## 27 自主 Agent 评测与升级路线

### 第一阶段必须交付的最小链路

真实商品进入系统并按条件筛选；一个自主 Agent 动态查询货源、核实同规格单件价；确定性利润工具和风险证据；候选、待确认、排除记录；参数快照、人工恢复、预算与调用轨迹。D7 验收此链路，随后继续完成内容、草稿、预测补货与经营模块。

### 如何证明自主性有价值

先整理 30 至 50 个标注场景，覆盖配件低价、套装差异、旧货源失效、缺重量、风险证据不足、局部改稿、渲染失败、缺历史、版本变化和中断。A 与 B 使用相同工具、数据、模型及预算条件，对真实模型多次运行，运营核对结果；未来 C 用同一集合对照。

| 指标 | 验收或对照方式 |
| --- | --- |
| 任务完成率 | 交付物正确且证据完整的比例；部分结果和待确认单独统计。 |
| 商品与报价错误 | 标注商品中误排比例、规格件数和单件报价错误；未知不能自动排除。 |
| 人工与运行效率 | 每个有效候选的人工分钟数、接管次数、完成耗时中位数与 P95。 |
| 成本 | 每个有效审核包的 Token、模型金额、图像视频及基础设施费用。 |
| 恢复与权限 | 重复恢复、共享预算、跨店铺拒绝、确认版本、远端未知状态。 |
| 预测与补货 | 按时间留出回测，比较简单基线 MAE、WAPE 和偏差；不泄露未来数据。 |

建议效果目标为 B 相比 A 完成率提高至少 10 个百分点，或人工核查时间减少至少 30%，且误排与报价错误不恶化。关键越权、未经确认发布及测试值冒充真实值，在验收样本中必须为零。以上为待评测目标，不是已有成绩。

### 升级路线

阶段一：单 Agent 与专业工具，完成真实业务验收。阶段二：优化工具说明、检索、上下文和模型选择，按需求引入知识检索。阶段三：当不同领域上下文频繁混淆、权限与模型需求分化或独立研究并行收益明显时，试验主 Agent 加三个专业子 Agent。

C 相比 B 应显著提高完成率或降低复杂任务耗时，并满足批准的成本。只有商品数量增长时先扩 Worker、缓存及采集能力，不因 ASIN 数量自动增加 Agent。自由群聊、递归委派和自改规则继续暂缓。
