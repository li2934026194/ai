# PACK 16c 报告：解释评测「数字一致性」回归的定位与修正

日期：2026-11-19　作者：项目大脑（主 Agent）

## 一、现象

PACK 16 之后的全量评测（RUN 1，`docs/eval-raw.json` 188556B）出现：

- 问数命中 50/50（100%）
- 解释四要素 30/30（100%）
- **解释数字一致 19/30（63.3%）**
- 用例通过 19/30

PACK 15 时该指标是 30/30。也就是说：改了 σ 之后，解释侧数字一致性掉了 11 条。

## 二、根因（不是模型答错）

逐条读 `mismatches` 发现，11 条失败**全部只有一项差异：「金额」**，形态统一为
`金额: 期望 4200（容差±21），文本数字 [...]`，而回答文本里已经出现新数字。

对照 `tests/cases_explain.json` 头部：

- `frozen_at: 2026-11-18`
- `note`：db 用例的 `expect` 由 `api.service.sku_detail` 在 2026-11-18 读出后冻结。

结论：**PACK 16a 把 σ 从「全样本拟合残差」换成「回测各窗口样本外合并残差」、并接通 ar1，
建议量随之变化，但 2026-11-18 冻结的 `expect` 没有跟着重算。**
评测器拿旧基准去比对新答案，必然判不一致。这是基准过期，不是生成侧或判定侧的 bug。

## 四、必须点明的业务后果

**8 条用例（6 个 SKU 组合）从「订 300 件」变成「无需补货」。**

链路：

1. σ 变准（取样本外残差）→ σ_LT 下降（如 SKU-017：25.19→19.55）
2. 目标库存 `target = μ×(LT+RP) + z×σ_LT` 随之下降约 10 件
3. `raw = target − (在手 + 在途)` 从「正但极小」掉到 ≤0
4. 原本 `raw>0` 时会被 MOQ 300 抬升成 300/660 的那条链路，整条断开 → qty=0、资金=0

实测（`ds_00b31ed333b05de698c0`）：

| SKU | μ | σ_LT | SS | target | 在手 | raw | qty | 资金 |
|---|---|---|---|---|---|---|---|---|
| SKU-008 | 8.7667 | 28.2073 | 53.0522 | 649.1856 | 678 | 0（负值截零） | 0 | 0 |
| SKU-010 | 8.7889 | 21.9060 | 41.2008 | 638.8453 | 678 | 0 | 0 | 0 |
| SKU-017 | 8.7722 | 19.5462 | 36.7624 | 633.2735 | 279 | 354.2735 | 360 | 3600 |

这不是数字微调，是语义变化：**建议量在 MOQ 门槛附近对 σ 极敏感**。
σ 只要上下浮动 10 件，判定的就是「订 300 件」和「不用订」两种截然不同的结论。
属于必须公开的残余风险，不是 bug，也不许用「把 MOQ 调小」之类改规则的方式掩盖。

## 五、防循环论证：新增 T19

基准按 as-built 重算，天然存在「基准与代码同源」的循环风险。为此新增独立算式校验
`TestDerivationIdentity::test_t19_derivation_identity_independent`：

- `SS = z × σ_LT`（1e-9）
- `ROP = μ × LT + SS`（1e-6）
- `target = μ × (LT + RP) + SS`（1e-6）
- `raw = max(target − (在手 + 在途), 0)`
- `qty = ceil(max(raw, MOQ)/整箱)×整箱`；`资金 = qty × 单价`（raw≤0 时两者必须为 0）

测试不复用 `build_suggestion` 的结论，只用它返回的原始量另算一遍，能抓住
「σ_LT 没真正进入 SS」「RP 被错用」「qty 与资金不自洽」这类接线错误。

## 六、复评结果

`python -m tests.eval_qa`（复用解释缓存，不重新生成文本）：

- RUN 2：**问数 50/50（100%）、解释数字一致 30/30（100%）、四要素 30/30、用例通过 30/30**
- LLM 调用 50 次（解释 26 个缓存键全部命中）
- 写副作用：全部用例 `write_side_effect=False`
- `pytest tests -q`：**75 passed + 6 subtests（34.42s）**

**关于耗时的说明**：RUN 2 记录总耗时 22428.8s、均值 448.58s/次，是因为评测期间客户端两次离线
（休眠/断网）被计入墙钟时间，**不能作为性能结论**。真实单次解释生成在 RUN 1 是 54.56s/次。

## 七、欠账与风险

1. **MOQ 敏感区**：σ 在临界值附近会让建议量在「0 / 300 / 660」之间跳变。当前无「临界提示」，
   用户看到 0 可能会误以为系统漏算。后续应在 `derivation` 增加 `raw_before_clamp` 与「距 MOQ 门槛多远」的提示。
2. **基准重算的正当性边界**：本次改 `expect` 的前提是「口径真实变化 + 逐条留痕 + 问题文本不变」。
   任何人再改基准，必须同样留下 `revision_changes`，否则视为红线破坏。
3. **评测耗时不可用**：机器休眠会污染 `total_ms`，脚本应记录「有效调用耗时」而非墙钟。
4. 解释缓存键仍是 `dataset_id|sku`，若同一 SKU 换路线/目标，缓存会串味（16b 引入 route/objective 后
   key 未扩展）。当前评测未覆盖，需在 PACK 18 修。

## 八、结论

19/30 是**基准过期**，不是模型退化；修正后 30/30，且新增独立算式校验防止基准与代码一起漂移。
真正需要盯的不是这个分数，而是「6 组 SKU 由订 300 件变无需补货」这一语义变化——
它说明 σ 修正已经真实地改变了业务决策，这是修复生效的证据，同时也是必须写进风险的敏感点。
