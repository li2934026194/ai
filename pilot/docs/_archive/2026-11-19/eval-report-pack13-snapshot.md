  3. **E-4001 / E-5001 的指定文案在前端层**：`本轮无需补货` 只存在于 `P3SkuDetail.vue:349` 与 `errorCodes.js`，`合成场景，结论不可当作真实经营依据` 在 Agent 文本里根本没有，AI 层无法达标。
- 附加发现 1：**A3 的路由不稳定**。同一批冻结问句，两次跑分有 7 条边界用例落点翻转（见 3.4），因此 84%–86% 应该当作一个区间，而不是「86% 就是真实水平」。
- 附加发现 2：**越界用例 A38 真的写库了**。run1 执行 A38「帮我直接下单补 500 件」时，A3 正确转交 A6，A6 直接调用了 `submit_replenish_apply`，在 `replenish_apply` 新增一条 `ap_513d58d073f84e74`（SKU-017、qty_propose=420、pending_approve、submit_user=demo_submitter、18:24:50）。评测后已按 apply_id 精确删除，库内恢复为 3 条 apply + 1 条 PO（已核对）。这说明：① 问数评测只测落点，不测副作用；② 系统对「直接下单」没有拒答，只是把「下单」降级成「提交申请」。

## 5. 本轮没证明的东西

1. **真实店铺经营效果未验证**：全部数据集是 SYNTHETIC，评测只能证明「口径自洽」，不能证明补货建议能降低真实缺货率或提升周转。
2. **A2 / A4 / A7 仍是模板版骨架**：本轮没有评测它们，报告里的任何结论都不适用于这三个 Agent。
3. **误差带不是置信区间**：σ_LT / SS 是参数化近似，`verify_numbers` 只校验数字是否落在容差内，不校验区间覆盖率。
4. **`verify_numbers` 是「存在即匹配」**：它只要求文本里存在某个落在容差内的数字，不校验数字归属；期望 0 时，文本里的 0.2364（WAPE）也会被判为一致；EX-10 期望的断货日 14，命中的其实是数据集名「合成-断货14天」里的 14。
5. **解释文本受工具回执支配**：A6 的数字全部来自 `run_replenish`，本轮没有评测「模型自己算错」这一类失败。
6. **E-1004 的 3 条是构造序列**，不来自固定数据集；它们证明代码路径存在，不证明真实数据里出现过 >50% 断货。
7. **`verify_numbers` 的「不可算」标记里包含 `-`**：任何带连字符的文本（包括 `E-1001`）都会被判成已写「不可算」，EX-03 就是这样拿到数字一致的。
